## Incremental commit strategy

One commit per task, in the order above:

1. `test(disabled): pin that an unlocked panel stays hidden while the addon is stood down` (M1-T1; red cases committed together with M1-T2, or kept local until M1-T2, whichever the gate allows. Never commit a red suite)
2. `fix(canvas): the stand-down latch outranks the unlock decoration` (M1-T2, with M1-T1's cases, F-001/F-006)
3. `fix(combat): drive combat visibility off the transition event and the combat flag` (M2-T1 + M2-T2, F-002/F-005)
4. `fix(canvas): release mismatched frames before acquiring, so a profile swap reuses its frames` (M3-T1 part + M3-T2, F-004)
5. `fix(recover): bound offsets in the frame's own scaled units` (M3-T1 part + M3-T3, F-003)
6. `fix(schema): one grid-size maximum` (M4-T1, F-007)
7. `fix(editor): the per-panel Unlock tick follows the real unlock state` (M4-T2, F-008)
8. `docs: correct comments that describe superseded mechanisms` (M4-T3, F-009)

Because the gate must stay green at every commit, each red-first test lands in the **same** commit as its fix. The red run is observed locally and recorded in the commit body (`red before: <case name>`).
